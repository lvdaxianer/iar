# Design

## Context

详见 `proposal.md`。当前 Runtime 已将内置自我介绍包加入默认插件集合，
但筛选逻辑无条件重新加入它；语义 Prompt 又把身份询问规定为 `unknown`。
模型上下文虽然已有能力描述字段，但需要明确它是所有相关模型调用的基础目录，
而不是只有自我介绍结果才可使用的数据。

## Goals / Non-Goals

**Goals:**

- 让真实 LLM 在自我介绍 Plugin 启用时能选择稳定的 Function ID。
- 让 Agent 创建时的禁用集合统一控制安装、候选、模型上下文和自我介绍清单。
- 让未命中自我介绍的普通输入仍能得到当前启用能力目录作为上下文。
- 用测试覆盖真实 Prompt 语义、默认开启、显式关闭和执行结果。

**Non-Goals:**

- 不改变 Pi bridge 的既有处置语义；仅增加向后兼容的 pass-through 能力上下文字段。
- 不让回复模型直接选择或执行 Plugin。
- 不改变已有 Plugin 的生命周期、授权和确认规则。

## Decisions

### 1. 由候选描述决定自我介绍是否可路由

语义 Prompt 将“身份/能力介绍”绑定到当前候选中存在的自我介绍 Function；
普通寒暄和无关问题仍使用 `unknown`。这样模型不会在 Plugin 已关闭时生成
一个不存在的 Function。相比在路由层按字符串强行改写 `unknown`，该方式保留
语义模型的单一输出契约，并使关闭配置自然生效。

### 2. Runtime 以筛选结果作为唯一有效能力集合

`disabledPluginIds` 先过滤外部 Plugin；自我介绍包仅在未被禁用时追加。
PluginHost 的 descriptors 继续作为语义、路由、回复和自我介绍的共同来源。
相比在每个调用点分别过滤，集中在 Runtime 安装边界能避免关闭能力重新出现在
某条模型路径中。

### 3. 保持能力目录为模型数据，不授予权限

能力描述继续放在受控的结构化上下文中，并标注为不可信数据；最终执行仍依赖
当前注册表、授权、策略和确认。自我介绍 Plugin 的输出仅供回复模型组织文本，
不允许通过额外提示词扩展能力集合。

### 4. 对有效但错误的 unknown 保留安全边界

本次先修正 Prompt 和配置筛选，不把任意 `unknown` 通过字符串规则直接升级为
动作。Scripted provider 作为离线测试/故障兜底继续保持现有匹配器；真实 LLM
只要根据候选和 Prompt 返回有效自我介绍 Function，即进入现有两阶段路由和执行。

## Risks / Trade-offs

- [风险] 真实模型仍可能返回错误的 `unknown`。→ 增加 Prompt 回归测试，并保留
  结构化 unknown 的安全兜底；后续若线上仍误判，再单独评估确定性预分类。
- [风险] 禁用自我介绍后，身份问题不会得到能力汇总。→ 这是显式配置的预期行为，
  测试验证其进入普通未知输入路径。
- [风险] 能力目录过大增加模型上下文。→ 继续复用 PluginHost 有界 descriptors，
  不扩展现有数量和描述长度边界。
- [风险] 旧 Pi Host 忽略新增字段。→ 字段保持可选，旧客户端继续按原 pass-through
  行为运行；新版 Pi Host 优先使用字段构造模型上下文。

## Migration Plan

无需数据迁移。新 Agent 默认行为保持自我介绍启用；只有显式把内置 Plugin ID
加入 `disabledPluginIds` 的创建请求会改变行为。回滚时恢复旧 Prompt 和追加逻辑
即可，不影响持久化数据格式。
